# WAP-301 member phone navigation keyboard focus

At 375 px on baseline `7c4c8e3ff3ced1b0f4e0d4cd37ab29ba147c9ee2`, actual Tab traversal focused Job board at x = 341.0625–448.375 inside a rail clipped to x = 16–359. Only 16.7% of the target remained visible after 250 ms. Independent forward/backward traversal found seven clipped labels and ten clipped focus rings. [WAP-301](https://linear.app/mikebeezy/issue/WAP-301/member-phone-navigation-fully-reveal-keyboard-focused-tabs) records the duplicate check and bounded finding.

The [production member navigation](../../components/portal/MemberPortalTopNav.tsx) now centers a keyboard-focused destination using the existing horizontal active-tab calculation. Its focus handler checks native `:focus-visible`; pointer focus does not invoke the helper. The [phone rail CSS](../../css/portal.css) suspends proximity snapping while a link has visible keyboard focus, preventing snapping from undoing that position. Swipe/pointer snapping resumes when keyboard focus leaves. The existing nav ResizeObserver also recenters a keyboard-focused item as compact chrome changes geometry, preventing label expansion from moving that item outside the clip. Locale destinations, aliases, active-route matching, badges, prefetch policy, desktop layout and bottom-navigation behavior are unchanged. The helper scrolls only the list, without `scrollIntoView` or a document-scroll operation.

## Rendered verification

The real component renders in `/dev/member/jobs` with synthetic data and remapped destination URLs. Production mounts it through the authenticated member workspace shell without `hrefMap`. The fixture's extra Skip to navigation link is excluded from the defect claim; the regression reaches the first rail link by actual Tab rather than a fixed document tab count.

The committed [browser regression](../../tests/e2e/member-topnav-keyboard-focus.spec.ts) fails against the original source and passes against the candidate in all six light/dark × 320/375/768 px cases. Each case traverses all rendered fixture destinations forward and back (10 in the detailed receipt; production defines 13, and the three omitted fixture destinations are not individually certified), waits 250 ms for transitions/snap settlement, and verifies focus, at least four pixels of clearance on both sides, the visible ring, and unchanged initial document Y. The 375 px cases also scroll into compact chrome and repeat forward/backward traversal through its expansion, checking settled target/ring visibility while allowing inherited native focus scrolling. A CSS-only snap/scroll-margin experiment still clipped seven labels and eight rings; it was not shipped.

At 375 px, 38 detailed candidate per-link measurements across both themes show no clipped target or ring. Job board moves to x = 134.0625–241.375 inside the same x = 16–359 clip. Additional actual-source checks retain touch panning and restored snap, visible focus at 125% CSS zoom/768 px, and a hidden phone rail with no document overflow at 769/1440 px. Native history pathname changes mark and reveal My program while preserving nonzero document Y = 180 in both themes; these check the mounted component's route-state effect, not destination acceptance.

Normal top-of-page keyboard traversal preserves Y = 0. At nonzero Y, the existing compact chrome collapses labels to icons and native browser Tab can scroll the document toward the top as it expands. The first candidate left My progress clipped during that expansion; reusing the existing ResizeObserver corrects its settled horizontal position. The supplemental receipt retains the inherited native vertical scrolling and does not claim global scroll-position invariance. The candidate helper itself has only a horizontal list-scroll operation.
