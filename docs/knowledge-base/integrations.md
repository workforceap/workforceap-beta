## Supabase Auth, Postgres and Storage

**Purpose and boundaries.** Supabase Auth owns external identities and session validation. App users, role assignments, organizations, enrollment and workflow state live in Postgres through Prisma; matching an Auth identity does not by itself establish a portal role. Browser entry is [auth/client.ts](../../lib/auth/client.ts); server session/user access is [auth/server.ts](../../lib/auth/server.ts#L37); [middleware.ts](../../middleware.ts#L278) refreshes the cookie/session boundary. [supabase-admin.ts](../../lib/supabase-admin.ts#L1) is the privileged server client. Database access starts at [db/prisma.ts](../../lib/db/prisma.ts) and [request GUC context](../../lib/db/withRequestGuc.ts).

**Configuration.** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `POSTGRES_PRISMA_URL`, `POSTGRES_URL_NON_POOLING`, and wrapper fallback `DATABASE_URL`. Related application controls include `AUTH_TRUST_COOKIE_SECRET`, `ADMIN_MFA_TRUST_DAYS`, `STAFF_MFA_ENFORCEMENT`, `WAP_RLS_GUC_ENABLED`, and `PRISMA_FLATTEN_TX`. [Environment guards](../../scripts/lib/supabase-project-guard.cjs#L69) enforce demo/production mapping during Vercel builds; [operations](operations.md#database-and-rollback) describes migration limits.

**Storage.** Uploads use the same Supabase project. [Member resume upload](../../app/api/member/resume/upload/route.ts), [resume retrieval](../../app/api/member/resume/route.ts#L17), and [voice recording](../../app/api/member/voice-interview/recording/route.ts#L11) use the `member-resumes` bucket. The browser [video uploader](../../lib/portal/mockInterviewVideoUpload.ts#L26) asks the app for a signed upload, uploads to Storage, then finalizes through the app. Postgres owns profile/recording metadata; Storage owns bytes; a stored path does not prove bytes are readable. [Public asset validation](../../lib/storage/publicAssetUrl.ts) separately handles public asset URLs.

**Failure and verification.** Shared auth reads distinguish stale sessions from transient failures and allow one additional transient read; see [the auth boundary](architecture.md#request-and-authorization-boundaries) for the retry and cookie contract. An unsuccessful read still cannot authorize a request, so callers may return 401/403 or redirect, but transport failure does not justify clearing session or PKCE cookies. Missing default-org/DB access breaks Next page readiness. Storage routes return explicit preparation/sign/download failures. Start with [health readiness](../../app/api/health/ready/route.ts), the relevant mocked route suite, and [trusted authenticated smoke](../../.github/workflows/authenticated-portal-smoke.yml). A generated Prisma client is not a DB or Storage acceptance test.

## Resend and notification channels

**Reviewed policy: WAP-14 / PR 2258.** The shared Resend boundary suppresses reserved and configured fixture domains across every envelope recipient and returns a distinct skipped outcome. Keyed workflows preserve the same payload and idempotency key across provider retries; placement-survey rows persist delivery/accepted attempt numbers plus the complete helper-level provider payload before egress, so ambiguous retries are resolved before mutable contact checks, remain identical even when member profile fields change or email is removed, and report the frozen recipient while intentional later resends freeze a new payload and key; bulk scheduled workflows share one route/delegation-scoped pacer and absolute request deadline. Next request work is retained only where source registers it with `after()` or awaits it before responding. These controls establish code behavior, not live credentials, mailbox delivery, or production acceptance.

## ElevenLabs voice and agent tools

**Purpose and ingress.** Private member/staff/employer/partner coaches and a public WIOA voice flow mint provider sessions on the server, then browser components connect with [@elevenlabs/client](../../components/portal/PortalVoiceSession.tsx). Entry examples: [resume coach](../../app/api/member/resume-coach/session/route.ts#L71), [interview](../../app/api/interview/session/route.ts#L35), [employer voice](../../app/api/employer/voice-session/route.ts), [partner voice](../../app/api/partner/voice-session/route.ts), [staff walkthrough](../../app/api/counselor/sessions/voice-walkthrough/route.ts), and [public WIOA](../../app/api/public/wioa-qualification/voice-session/route.ts#L15). [elevenlabs.ts](../../lib/ai/elevenlabs.ts) implements provider HTTP calls; [elevenlabsAgents.ts](../../lib/ai/elevenlabsAgents.ts) resolves the role/session contract.

**Configuration and authority.** `ELEVENLABS_API_KEY` plus role-specific agent names in [agentRegistry.ts](../../lib/elevenlabs/agentRegistry.ts#L40): `ELEVENLABS_INTERVIEW_AGENT_ID`, `ELEVENLABS_COUNSELOR_AGENT_ID`, `ELEVENLABS_COUNSELOR_STAFF_AGENT_ID`, `ELEVENLABS_EMPLOYER_AGENT_ID`, `ELEVENLABS_READINESS_AGENT_ID`, `ELEVENLABS_RESUME_COACH_AGENT_ID`, `ELEVENLABS_PARTNER_AGENT_ID`, `ELEVENLABS_WIOA_PREQUAL_AGENT_ID`, `ELEVENLABS_CAREER_BUSINESS_AGENT_ID`. This branch pin is separate from agent IDs and voice settings. That registry defines reviewed fallbacks, roles, exposure and allowed tools; historical migration IDs are not automatic runtime choices. The legacy `NEXT_PUBLIC_ELEVENLABS_*_VOICE_ID` browser voice settings no longer have a consumer: the unused `lib/portal/counselorVoice.ts` and `lib/portal/interviewVoice.ts` helpers were removed.

**State and egress.** [Portal context](../../lib/ai/elevenlabsPortalContext.ts) derives server context from app state; resume sessions explicitly bound the text sent to the provider. The provider owns its remote agent configuration and live conversation. Checked-in patches and [sync scripts](../../scripts/elevenlabs/sync-member-agent-tools.mjs) describe intended remote configuration; they do not prove it is synchronized. Test [voice session boundaries](../../tests/api/voice-session-boundaries.spec.ts), [gateway routes](../../tests/api/agent-gateway-route.spec.ts), [registry](../../lib/elevenlabs/agentRegistry.test.ts), and [provider session behavior](../../lib/ai/elevenlabsSession.test.ts). ## Coursera B4B, Enterprise and xAPI

Coursera owns its course catalog, memberships and provider progress. WorkforceAP owns member/organization linkage, approved program curricula and local enrollment/workflow state. Provider evidence is persisted and reconciled; “course name resembles program name” is not an identity rule. Start with [enrollment flow](../COURSERA-ENROLLMENT-FLOW.md), [identity matching](../COURSERA-IDENTITY-MATCHING.md), and the current implementation below.

**Required organization and lookup coverage.** [The B4B client](../../lib/coursera/b4bClient.ts) requires a non-empty `COURSERA_ORG_ID` and raises `B4BConfigurationError` when absent; there is no default provider organization. [Enrollment lookup](../../lib/coursera/enrollPort.ts) qualifies its positive/negative cache by provider organization and normalized email. An exhausted or inconsistent roster scan raises `CourseraRosterIncompleteError` rather than caching a missing learner or proceeding to an invitation. Only a complete scan can establish absence. Organization changes during pagination also fail the scan. [Learner progress caches](../../lib/coursera/learnerProgress.ts) include the provider organization, including the program-ID cache; incomplete or unavailable provider evidence must not be presented as known zero progress.

Before deploying this required-configuration change, verify that `COURSERA_ORG_ID` is provisioned for the intended deployment target using environment-name metadata, then independently verify the credential/organization pairing with an authorized read-only provider check. Do not record secret values or infer that a present name proves the correct pairing. Source tests and generic app readiness cannot satisfy this configuration gate, and no sync, invitation or replay is required to check it. [Organization configuration tests](../../tests/lib/coursera-org-configuration.spec.ts) and [roster coverage tests](../../tests/lib/coursera-enroll-roster.spec.ts) establish the local failure/cache contracts.

**Reconciliation contracts (September 19 source changes).** The staff roster resolves assignment through the same policy as the member training view: primary durable enrollment and pinned curriculum, equivalent legacy enrollment when applicable, then an explicitly labelled legacy-only fallback when no enrollment exists. Observed learning never chooses a formal assignment. Grade selection is independent of learner activity; the roster's Last active chooses the latest dedicated course/provider activity timestamp or sign-in and labels its source. Import receipt and database update times are not learner activity. See [roster facts](../../lib/admin/studentsRosterFacts.ts), [bounded SQL](../../lib/admin/studentsRosterEnrichmentQuery.ts), and [roster tests](../../tests/lib/students-roster-enrichment.spec.ts).

Coursera xAPI scaled scores are grades, not course progress. Future xAPI activity writes use a validated statement timestamp and preserve newer known activity; undated provider completions do not fabricate a learner activity date. The REST course-fact adapter explicitly classifies its validated course activity; item scores do not become course completion. Polling preserves explicit completion separately from item progress. Direct learner reads carry complete/capped/unavailable coverage, and B4B continuation metadata is scoped to the provider organization and WAP organization. A successful partial window is not a full-provider reconciliation. Token issuance and statement receipt both require configured signing credentials. These are source contracts, not provider or deployment acceptance.

Hours/grade completeness and historical reconciliation remain separate from these code repairs. Existing raw hours cannot distinguish absent provider measurements from observed zero, and row-level source does not establish each measurement's provenance. Historical xAPI activity fields can contain receipt times written by earlier code; changing future writes does not repair those records. Do not infer a new assignment, approve a seat, replay events, rewrite historical progress, or activate an approved curriculum merely because an administrative report reveals a gap. Data repair needs the intended assignment, provider evidence cutoff, measurement policy, scoped preimages, and its own acceptance.

## Stripe and donation links

**Implemented financial paths.** [Stripe client](../../lib/stripe/client.ts#L3), [employer checkout](../../app/api/employer/checkout/route.ts), [direct subscription](../../app/api/employer/subscribe/route.ts), [partner Connect](../../app/api/partner/connect/route.ts), and [Connect transfers](../../lib/stripe/connect.ts) are provider egress. Ingress is [employer webhook](../../app/api/employer/webhook/route.ts#L8) and [platform/Connect webhook](../../app/api/stripe/webhook/route.ts#L19), which verify raw-body Stripe signatures. Stripe owns financial objects; app organization/employer/subscription/partner records hold local linkage and status. Confirm both when reconciling.

**Configuration.** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_CONNECT_WEBHOOK_SECRET`; price names in [client.ts](../../lib/stripe/client.ts#L38) and [pricing.ts](../../lib/stripe/pricing.ts): `STRIPE_BASIC_PRICE_ID`, `STRIPE_STARTER_PRICE_ID`, `STRIPE_GROWTH_PRICE_ID`, `STRIPE_ENTERPRISE_PRICE_ID`; `NEXT_PUBLIC_SITE_URL` for return URLs. `EMPLOYER_PRICING_ENFORCED` is a source constant currently false. That describes product gating; it does not mean retained Stripe routes are absent.

**Failure and verification.** Missing Stripe keys throw; signature failure returns 400 and processing failures return errors for retry. Every employer/organization transition reads the persisted binding and revision, retrieves the canonical Stripe subscription outside the short database transaction, validates subscription/customer/owner identity, then compare-and-set writes the binding, canonical status, diagnostic event cursor, and incremented revision. A lost CAS discards the provider snapshot, rereads, and refetches; exhausted contention and unresolved ownership return non-2xx for Stripe retry. Any accepted canonical-canceled transition derives the basic terminal tier/mirror; later same-binding checkout, invoice, or canonical snapshots cannot overwrite it. Checkout and direct subscribe may replace only a different subscription whose metadata names the exact current predecessor; mirror rows are written only inside the successful atomic employer commit. The additive rolling migration leaves binding/cursor columns nullable, adds revision columns at zero, and performs no status-derived backfill; NULL bindings require corroborating local subscription/employer ownership before adoption. Employer pricing remains disabled by `EMPLOYER_PRICING_ENFORCED`: the billing page exposes no checkout control, and both checkout and direct-subscribe APIs return before customer/subscription/session creation. Use designated test-mode financial fixtures and the relevant route tests; never infer charging or payout readiness from a price ID or package import.

**Donations use an external link.** The active Astro [donate page](../../marketing/src/pages/donate.astro#L18) sends donors to Zeffy; its corporate inquiry form opens an email client. This page does not evidence a Stripe donation checkout or in-app donation ledger. No application environment credential is used for that link. Verify navigation and the separately owned donation destination when that journey changes.

## Verify a provider change

Follow the specific entry route through its client, environment selection, persisted state and error response. Run the applicable Node/Vitest lanes described in [operations](operations.md#checks-and-ci), including test collection ownership. Then, when authorized, verify a designated isolated provider journey and inspect both app state and provider acceptance. Record the exact SHA, target, sanitized outcome and remaining gaps. This inventory was built from source only: no live API calls, messages, payment actions, provider changes or database operations were performed.
